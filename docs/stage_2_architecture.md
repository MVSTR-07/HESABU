# M-Pesa analyser: scope and privacy

Stage 2 keeps the Stage 1 screen style. No Canva styling, customer analyser or AI
work is included. Pure Dart modules in `lib/core/mpesa` expose parsing,
classification, analysis and serialisable result models. The dashboard routes
through the tool registry.

## Import and storage

Windows reads native-picker files into bounded memory. Android uses an
ACTION_OPEN_DOCUMENT local-only stream bridge, avoiding a plaintext picker-cache
copy; that bridge requires subsequent Android device validation. Imports are
limited to 25 MB, 50,000 transactions, 500 PDF pages and 8 MB extracted PDF text.
PDFium is bundled during the build. The reader disables HTTP access and uses
in-memory PDF bytes; no runtime binary download, cloud parsing or OCR occurs.

Real passwords exist only in the obscured dialog and transient import call.
Controllers are cleared/disposed, passwords are not database fields and native
errors are replaced with safe messages. Dart strings cannot promise physical
memory zeroisation. The public fixture password is only for fabricated data.

Source bytes, normalised transactions, warnings and computed results are saved
atomically inside the existing SQLCipher database, outside OneDrive. Schema v2
migrates v1 without replacing existing data/key. Identical source-byte hashes
reuse a saved record. The existing Windows secure vault retains the key across
app restarts; isolated native tests verify this with a separate vault entry.

Clear cache deletes M-Pesa sources/results and app-owned cached files while
preserving account/theme and Stage 1 demo payments. Full deletion destroys the
old key, clears owned database/cache files and creates a fresh empty database.
Neither action deletes the user's original selected files. Import locks prevent
navigation/deletion races. Test fixtures are synthetic; PDFs/CSVs and named
real-data folders are Git-ignored.

## Supported formats and limitations

For statements with drawn table borders, PDFium now reads the vector paths and
applies nested form transforms. The pure-Dart ruled-table reader identifies a
closed seven-column transaction grid from its header, assigns words to physical
cells and separates summary/footer tables. It does not infer row starts from
receipt glyph heights or column starts from centred headings. The native handle
is used only inside the public engine callback that suspends its PDFium worker;
no handle is retained, no PDF is rewritten/rendered/exported and no server is used.
An unruled supported table retains the previous text-position fallback. Once a
closed grid is identified, unreadable required financial cells reject the import
rather than switching silently to guesses. Empty descriptive cells are retained
as an explicit unavailable-description marker, classified unknown and warned;
no description, identity or amount is invented. Complex paths have resource caps.

The supplied first page contained a three-column summary, seven-column detail
table and two-column footer; the supplied second page had the detail/footer
tables. A local independent field comparison found zero mismatches in all 66
transactions (25 + 41), including receipts, timestamps, descriptions and monetary
cells. Only geometry and mismatch counts left those local comparison processes.
No real rows were saved as fixtures. Whole-statement sign-off still requires the
full local import and totals checks. See `evidence/mpesa-local-grid-verification.txt`.

CSV supports quoted fields, BOM, UTF-8/UTF-16LE, comma/semicolon separators,
common column aliases and preambles. Dates are strict Kenyan day/month/year or
ISO year-month-day; unzoned timestamps mean UTC+3. Failed transactions are
excluded with a warning. Ambiguous/malformed rows reject the complete import.
Amounts use integer cents, avoiding floating-point rounding.

PDF first reconstructs the seven columns from positioned text: receipt,
completion time, details, transaction status, paid in, withdrawn and balance.
Blank incoming/outgoing cells retain their direction and become zero; a missing
balance is rejected rather than invented. Summary sections are excluded, and
wrapped descriptions, split date/time cells and repeated page headings are
supported. A legacy plain-text fallback still requires three explicit trailing
amounts. Image-only/scanned PDFs and ambiguous layouts fail with
an actionable CSV alternative. Fabricated PDF/CSV equivalence is tested; support
for every historical Safaricom layout is not claimed. Never silently infer
ambiguous amount columns or commit real statements to expand tests.

The column-layout regression fixture is a fabricated two-page portrait PDF,
generated by `tool/generate_mpesa_layout_fixture.py` from the fabricated CSV.
Tests compare every receipt, timestamp, description, amount and balance against
that CSV. No real statement was opened or used as a fixture for this repair.

When positioned extraction rejects a row, the on-screen diagnostic reports a
fixed reason code, PDF page number, candidate row number on that page, global
table-row ordinal and fixed names of missing/conflicting columns. These are
candidate-row positions, not receipt IDs. Extracted text, dates, names, amounts,
filenames and passwords are never interpolated into that diagnostic. No separate
diagnostic file or upload is created. Passing fabricated tests does not establish
compatibility with the user's PDF; a local retry supplies the missing evidence.

The positioned-layout scan now continues through all pages after a page fails,
then reports counts grouped by reason and affected columns, with one example
per issue type (up to five). It reports the first layout failure per failing
page, not an exhaustive list of every bad row. Any failure rejects the whole
statement. Adjacent row bands share baseline-based boundaries rather than
receipt glyph-top cutoffs, covering tight rows with different glyph heights.

Footer recognition now happens before receipt/row grouping, using fixed footer
phrases only when they start in the leftmost column. A transaction-shaped row
after a footer marker rejects the import rather than being silently removed.
Close computer-generated notices are covered by fabricated regression tests;
merchant descriptions containing Safaricom remain intact. Image-only stamps do
not contribute text. The user confirmed the approval stamp in their PDF is an
image, so no stamp filtering is applied. Selectable stamp text in other document
variants remains outside the verified fixtures.

## Analysis definitions

- Exact duplicates match receipt, timestamp, normalised details, amounts and
  balance. Subsequent copies are flagged and excluded from all aggregates.
  Reused receipts with differing data are flagged but retained (fees can share
  receipts). This is deliberately different from dropping all reused receipts.
- Classification checks reversals and Fuliza before general fees/transfers.
  Unknown transactions remain visible with a warning. Names/phone text are
  extracted from descriptions, not verified identities or merged customers.
- Money in/out are cash movements, including loans, repayments and reversals;
  they are not revenue/profit. Sender rankings use classified customer receipts;
  receiver rankings use transfers, tills and withdrawal agents. Rankings are
  gross and do not invent reversal links.
- Identified fees include explicit Fuliza costs. Principal repayment is not a
  fee. Bundled costs count only when a supported description states the fee;
  missing charges are not guessed.
- Daily, Monday-start weekly and monthly periods, hours and weekdays use Kenya
  time. Balance points are observed statement balances, not reconstructed ones.
- Large one-off: either direction is at least the configured KES threshold.
  Spike: an amount exceeds the configured multiple of the other positive amounts'
  median in the same direction, meets the minimum KES floor and has the minimum
  comparison count. Defaults: KES 100,000; 3x; KES 1,000; 3 comparisons.
  Thresholds can be adjusted and reports reanalysed locally.

Automated coverage includes parser/classifier/rules, real PDF password handling,
encrypted storage/migration/deletion, narrow/desktop widgets and the native
Windows vault/PDF/storage integration. See `stage_2_manual_test.md` and
`evidence/stage-2-windows-storage.txt`. User manual sign-off is still required.
